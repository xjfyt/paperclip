# 评论目标绑定、身份隔离与撤回草稿验收

日期：2026-10-27。源码基线 `95682653`；覆盖普通评论、带运行设置/重指派评论、Agent Chat首次创建和新旧输入框撤回恢复。以下是待执行浏览器清单；823项自动回归不等于真实浏览器/API已通过。

## 准备与记录

- 使用隔离测试组织、任务A/B及Agent A/B，自动执行与通知关闭；正文使用明显不同的脱敏标记，例如 `A 原稿 {{keep}}` / `B 新稿`。准备同公司、跨公司、同用户换session、换用户四组情境，禁止对生产任务制造错误或真实收费调用。
- 经典 `IssueChatThread` 与新版 `TaskChatThread → TaskChatComposer` 分别执行；中文、英文、西班牙语、日语分别核对反馈，另在同一挂载页面切语。记录应用提交、浏览器/OS、目标、身份、请求阶段及结果“通过／失败／未执行”。
- 在受控夹具中分别延迟查询取消（`onMutate`等待期）、会话创建、发送响应和撤回响应；浏览器网络慢速不一定稳定命中这些阶段，无法建立对应时序时记未执行，不把普通成功路径当作竞态验收。
- 网络证据只保留方法、脱敏 company/issue/agent/comment ID、nonce及必要状态；不导出cookie、token、完整缓存或本地存储。不因“尽可能完成”而扩大到未授权外部调用。

## TARGET：导航不能改写已开始提交的目标

1. 在任务A输入原稿、选附件，分别走普通发送与带运行设置/重指派发送；在查询取消尚未结束、API尚未派发时导航B，再放行。请求必须仍指向A，正文、附件ID、nonce、模型/effort/负责人参数来自发送时快照，不得把A正文发给B。
2. 再在API已经派发后导航B，分别返回成功、明确失败、未知结果。保持同一身份时，成功/回滚/失效刷新只作用于A的对应缓存；B正文、评论、任务状态和附件不变，不显示A的旧乐观回声或错误toast。
3. 在B输入新稿后让A响应完成，确认A的响应不能清空B、改写B运行设置或把旧正文恢复到B。返回A查看真实结果，不因导航自动重试或追加另一条消息。
4. 对多个明确提交分别记录其原nonce与目标；切语/导航不生成替代身份。重复操作检查既有pending门控和请求次数，但不把“不同明确提交”错误合并；未知结果不能由重复点击变成无身份的新提交。

## CREATE：首次会话按公司、用户、session、Agent隔离

1. 在尚无会话的Agent A发送草稿，让 ensure/create保持pending，切换另一公司或Agent B并开始B的首次会话；A/B各使用自己的创建promise与目标，不能复用单一全局创建槽位。
2. 交换A/B成功与失败的返回顺序，确认A旧失败只清理A槽位，不清理B仍在途的promise；相同完整scope可去重，不同公司/用户/session/Agent不能混用。
3. A创建完成后，普通及带运行设置的后续评论都只能提交到A返回的正确会话；响应中的company、conversationAgent/user或已有会话ID不匹配应拒绝，不写错误会话缓存，也不继续发评论。
4. 在创建前及创建等待中分别切换用户/session或清空认证缓存；旧回调不得继续派发、写入任务/会话缓存或刷新新身份列表。当前授权无法确认时保持失败边界，不能把“缓存已清空”当成原本的本地匿名身份。

## ACTOR：请求全过程使用原身份边界

1. 普通与带设置两条路径均测试：提交前、查询取消等待中、请求发出后，分别换用户和仅换session。派发前已失配时不得发送或乐观写私有缓存；已发出的请求不能假装被浏览器撤销。
2. 对旧请求分别返回成功、明确错误、未知结果：只允许清理旧乐观记录，不向新身份私有缓存写成功结果、回滚旧快照或发旧toast；settled也不得借新身份刷新旧数据。
3. 在乐观撤回后、正式回执到达前换身份，旧回执不能触发新身份去撤回旧评论。若撤回请求已发出，在其await期间换身份，迟到成功/失败同样不得写缓存、刷新、恢复正文或通知新身份。
4. 对已持久化排队评论也执行撤回pending→导航B、撤回pending→换用户/session、卸载→清缓存→迟到成功/失败；B及新身份不受影响。保存的旧撤回回调再次调用应拒绝，不向新任务重发撤回。

## RESTORE：恢复结果必须真实，不能覆盖较新的工作

1. 在当前已挂载任务的空/仅空白、安全输入框撤回非空原稿：`restoreDraft`应返回true，逐字恢复空格、换行、Unicode/Markdown并同步持久化；显示“排队评论已取消”及“已恢复到输入框”说明。恢复本身不提交、不上传、不重建附件receipt。
2. 分别保留同事件刚输入的新文字、上传中的附件、已返回receipt的纯附件草稿、正在提交、未知提交标记；恢复必须返回false，内容/receipt/提交身份不变。新版还需检查队列编辑及调用方控制的新建任务模式，不能向其中注入旧正文。
3. false仍可表示撤回操作本身成功：只显示通用撤回成功，不显示“正文已恢复”。true/false两类在四语下复验；不能以toast存在推断草稿已恢复。
4. 对同一乐观排队消息连续双击撤回，确认已提交渲染快照只被消费一次、原正文最多恢复一次；同时追加另一条乐观消息不能被误删。正式回执到达后，按原comment ID执行必要撤回一次；再次点击已移除ID不重复请求。
5. 分别保留旧任务的composer句柄后切任务、卸载、再挂载；旧句柄restore/focus不能影响新输入框。当前句柄卸载后也失效；导航返回不自动复活旧恢复操作。
6. 撤回失败走既有错误回调且无未处理Promise拒绝；已经开始派发而无法撤回的409保持“已来不及撤回”语义，不假称取消或恢复成功。

## UNKNOWN 与文案边界

- 响应丢失/未知保存结果保留原稿、附件与原nonce，只能通过原有明确核对/重试入口处理；必须在原目标及有效身份下继续，同一逻辑重试保持原nonce。导航、切语、缓存刷新和恢复句柄都不能自动重放。
- 新反馈读取发生时的当前语言；旧toast不要求追溯改写。系统失败回退可翻译，服务端 `Error.message`、用户正文/名字、队列ID及技术标识保留原文；非Error对象不直接序列化成提示。
- 评论删除和加载历史在本批包含文案/既有契约回归，但不能把上述提交与撤回的目标围栏泛化成“全站所有mutation都已隔离”。
- **默认Enter行为、IME规则未改；本清单没有执行真实输入法/快捷键验收，不声称已测通过。** 后续真实IME检查须单独记录，不以jsdom事件或富文本mock替代。
