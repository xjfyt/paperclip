# 持久通知中心

路径：公司侧栏「通知中心」；API `/api/companies/:companyId/notifications`。管理写面限公司 owner/admin 或实例管理员；Agent 不能配置渠道。渠道配置与公司秘密引用由服务端校验；返回不含完整 Webhook、访问令牌或供应商原始错误。保存只校验，不发送。

## 开关与凭据

`PAPERCLIP_NOTIFICATIONS_ENABLED=true` 启用 worker 与业务事件钩子，默认关闭。`PAPERCLIP_NOTIFICATIONS_WORKER_ENABLED=false` 可暂停外部派发并继续事务入队，便于维护与无外发测试；恢复前先检查积压。部署前先备份数据库并应用标准迁移。凭据使用已有公司秘密存储，值为 JSON；配置中填写秘密 ID 和固定版本。

- 企业微信/飞书/钉钉旧 Webhook：`url`，需要签名时增加 `signingSecret`。飞书与 Lark 使用各自域名；设置页可明确选择飞书或 Lark。
- 钉钉应用机器人：公司秘密JSON可用`appKey`与`appSecret`，渠道配置robotCode/target；仍兼容显式`accessToken`。
- 微信公众号：公司秘密JSON可用`appId`与`appSecret`，渠道配置target（OpenID）、templateId、templateData；仍兼容显式`accessToken`。

应用凭据模式已通过0341私有加密缓存按需获取/刷新令牌；显式accessToken模式仍由外部维护过期，不混用两种模式。保存渠道只做本地校验，不换令牌、不发送消息。固定凭据版本在撤销后拒绝，不偷偷换到最新版本。配置变更新建 endpoint，旧投递仍绑定原快照。停用阻止进入 sending 前的投递，不能撤回已进入外部发送阶段的消息。

## 事件与投递语义

当前接入六类：`approval.requested`、`run.failed`、`coding.mr_ready`、`coding.ci_failed`、`coding.artifact_ready`、`budget.threshold_reached`。审批、预算会计事务、编码远端回执或产物清单持久化与对应入队同事务提交。重复同步由事件唯一键去重。`run.failed` 使用迁移 0337 的 PostgreSQL AFTER 触发器，覆盖旧/原生运行持久化的 failed/timed_out，不依赖易丢失的进程内回调。触发器只向原有 outbox 入队，不建立第二套总线、不发送网络请求。只为当时已启用的订阅和渠道记录最小引用与固定凭据版本。关闭运行时开关会停止派发；如需同时停止收集运行失败事件，应先停用该订阅或渠道。四语按订阅语言生成最小文案和公司前缀详情链接，renderVersion=2；已有投递保持原快照。失败运行使用 renderVersion=3，先在业务事务中冻结目标、版本、语言和公司/运行引用，worker 首次派发前持久化渲染后的文案和当前受信公开来源链接；后续重试复用这一快照。未产生有效渲染时不发送。仅发送资源摘要/引用，不发送完整业务 payload、代码或日志；不默认 @all。

唯一键 company/event/subscription 防重复入队。数据库原子领取和 lease UUID 防迟到回写。过期 claimed 可以重领；过期 sending 变为 indeterminate，不自动重发。平台 accepted 不等于已读，也不代表业务审批完成。测试发送使用显式确认和稳定 requestId；结果未知时先核对外部平台，不重复点击创建新测试。管理员可以在核对后通过显式重试 API 同时确认已核对结果、接受重复风险，以原快照创建新投递；原未知记录不改成成功，同一个重试 requestId 只入队一次。

共享目标间隔保存在数据库，通过事务 advisory lock 序列化：飞书默认 1 秒，其他渠道 3 秒，均为保守产品默认，不是声称所有产品有相同官方配额。429 按 Retry-After 和退避，最多 5 次/30 分钟；其他错误按 rejected/indeterminate 记录。业务错误码不盲目重试。超时、异常响应与 5xx 保持未知。

## 验证与限制

五驱动有协议单测（签名输入、字节长度、业务码、模板字段、未知结果）；真实 HTTP/PostgreSQL 集成覆盖回滚、幂等、双 worker 竞争、过期领取、sending 恢复、迟到回执与跨公司外键。真实群、公众号权限和 token 刷新均未验收。设置页四语已构建与类型检查，并在助手云桌面真实Chrome中检查四语暂停状态、四条待投递记录、禁用测试发送以及独立页面标题；未启用真实外发，不把该检查算作真实平台送达。

设置页现已提供六类事件订阅的启用/暂停、派发开关状态、脱敏原快照预览及双重确认后的显式重试。切换公司会重置表单；迟到的预览响应不会替换当前已确认目标。配置修订 UX 现已接入；供应商对账自动化尚未完成。此文不是完整通知能力验收报告。回滚先关闭开关和 worker，保留台账，再回退应用；不删新表清除未知状态。

公众号 templateData 支持单次展开 {{title}}、{{text}}、{{resourceId}}；未知占位符、畸形模板和超长值拒绝，不进行动态对象求值。模板渲染失败保留 rejected 投递，不回滚原业务操作；缺少有效渲染快照的投递不可显式重试，需先修正配置并重新核对业务事件。


## 应用令牌生命周期（0341）

- 仅企业钉钉应用和微信公众号使用本功能；不是Casdoor登录或个人WorkBuddy OAuth，也不读取通讯录做健康探测。
- 钉钉使用官方应用令牌POST契约appKey/appSecret、accessToken/expireIn。公众号使用稳定令牌POST契约，并固定force_refresh=false，避免主动使其他服务持有的令牌失效。
- 有效期按实际响应计算，不假定固定两小时；必须为有效正整数，超过一天的异常值拒绝。剩余不超过30秒时等待再获取，不发送临近过期令牌。
- 缓存按公司、秘密ID、明确版本与渠道种类分区，应用身份摘要固定。已有版本的内容突然改变会拒绝，轮换须创建新版本/渠道；旧积压不会转用新凭据。
- token用现有AES-GCM提供器加密，密文绑定缓存ID、公司、秘密引用/版本、渠道、身份摘要、代次及过期时间。不进入通用Agent秘密绑定，也不在设置接口返回。
- 多worker共享PostgreSQL租约，30秒租约与10秒请求超时。进程重启可复用缓存；过期租约可重领，迟到响应无法覆盖新代次。凭据停用或删除在刷新前后及实际投递前重新检查。
- 失败发生在消息派发之前：429/暂时性网络故障可以有限重试，错误凭据拒绝。忙租约/冷却等待不消耗发送尝试，但仍受队列重试窗口约束；实际预检失败计入最多5次/30分钟策略。消息已开始发送后的未知结果保持indeterminate，不能通过刷新令牌自动重发。
- 建议同一公司同一应用的渠道复用同一秘密ID/版本，避免多个重复凭据引用造成无谓的令牌获取；跨公司不共享令牌。
- 缓存校验失败不静默忽略：先核对主密钥与数据库备份，或在授权后换用新秘密版本。不得删未知消息记录来恢复派发。

本切片27项协议/加密单测与10项真实数据库用例通过；真实租户和送达仍未验收。微信文档链接由腾讯官方API目录确认；协议细节另外核对公开SDK源码，不能把这一交叉核对说成当前账号资格验证。

参考：[腾讯公众号API目录](https://cloud.tencent.cn/document/product/1301/100187)、[WeChat SDK稳定令牌实现](https://github.com/silenceper/wechat/blob/v2/credential/default_access_token.go)、[DingTalk SDK令牌契约](https://github.com/DingTalk-Real-AI/dingtalk-channel-sdk-python/blob/main/SPEC.zh-CN.md)。


## 渠道配置修订（0342）

配置修订以expectedVersion做并发比较；成功生成下一版本、保存操作者和完整非秘密配置历史，并原子暂停渠道。保存不获取token、不发送消息。渠道kind不能原地更换，须新建独立渠道。旧安装在迁移中保留v1快照。

旧队列保存原目标、秘密引用/版本和配置版本；修订绝不重写旧队列。再次启用前明确核对：启用会恢复仍有效的旧快照，而非自动转投新地址。已进入sending的消息不能通过暂停或修改召回。撤销旧秘密仍会阻止它被后续使用。

启用/暂停和测试发送携带expectedVersion；旧客户端省略时只对应v1，不能无意启用或测试后来被修改的目标。冲突返回409，保留输入并要求重新读取；历史查询同样只限公司管理员，最多返回100个版本，不返回Webhook/token/appSecret。


## 投递人工核对（0343）

GET/POST deliveries/:id/reviews提供不可变核对记录，限定公司管理员。操作者明确确认后记录“报告已受理/报告未受理/仍未确认”和不含秘密的简要依据；它是人工报告，不伪装成供应商自动回执或C3验证。

记录绑定投递ID、原传输状态/attempt、操作者与幂等requestId。同键同内容复用记录，内容或操作者不同拒绝409；仍在发送中不能核对，旧页面状态/尝试次数变化也拒绝。核对绝不更改原state/receipt/snapshot、不自动启用渠道、不发送或重试。需要重试仍走既有原快照预览及重复风险确认流程。

每条投递保留最近100条核对历史。供应商自动查询适配仍需按各官方产品实际查询能力单独实现；没有查询接口的Webhook不能通过缺少回执推定未送达。请勿把凭据或原始客户日志贴到核对依据中。

## 严重程度与有限精确重复合并

订阅策略 `minimumSeverity=info|warning|critical`、`mergeWindowSeconds=0..300` 通过公司管理员 API `PATCH subscriptions/:id/policy` 保存；默认 info/0，保持原行为。保存不发送，仅影响之后入队的事件，既有快照不追随策略修改。审批与预算为 critical，始终绕过过滤与合并；失败运行与 CI 失败为 warning；MR 和产物就绪为 info。停用订阅/渠道仍是独立的明确暂停。未知事件严重程度按 critical 保守处理，损坏的策略回退为不过滤、不合并。

这是有界的“精确重复合并”，不是跨资源消息摘要或告警升级系统。相同公司、订阅、事件类型、资源，以及完整冻结配置、收件人、秘密版本、语言、渲染内容与策略的消息才可合并。第一条建立固定最多 300 秒窗口并延迟派发；后来的相同消息不延长窗口。每个业务事件仍有独立台账，重复项标为 `merged`，`mergedInto` 引用原投递；过滤项标为 `filtered`，不伪装成功或供应商受理。若首条后来失败/未知，合并项仍链接该真实结果，不自动重新派发。原首条可按已有人工确认流程处理。

业务事务中的数据库 advisory lock 序列化窗口查找与插入，窗口和引用在数据库持久保存；仅未尝试的 pending 首条可接纳合并。已领取、重试、sending、结果未知或显式人工重试不再参与合并。固定窗口不改变现有目标限流、发送租约、重试上限或未知结果不重发规则。运行失败触发器仅冻结严重程度与策略并过滤，不合并不同运行；同一运行原事件唯一键继续去重。

策略单测覆盖阈值、关键事件绕过、边界隔离、固定窗口和锁顺序；这些是本地单元证据，不是实际 PostgreSQL 并发、供应商 C3 送达或 C4 业务闭环验收。迁移、触发器和页面集成后还需实际数据库事务/竞争测试和页面验证。


策略保存要求 `expectedVersion` 与订阅 `policyVersion` 一致，成功原子增加版本并在同一事务写审计；审计失败回滚策略。旧版本返回 409 和当前版本，不覆盖他人修改。页面保留冲突草稿，后台刷新不会替换它；必须明确选择“丢弃草稿并重新加载策略”，再编辑提交。保存不启用暂停订阅、不发送或重试。事件快照也冻结策略版本，不把两次不同修订的窗口混为一组。


## 配置版本验证与人工证据

新增渠道“配置验证”入口，按 endpoint/configVersion/凭据安全代次查询最新观察，不把旧成功覆盖新失败。凭据禁用再恢复不会复活旧验证；暂停渠道不等于撤销凭据。0356迁移固定新投递代次，旧行不回填。

C2报告、C3实连、收件观察与C4审批场景均为明确人工申报，machineVerified始终false；HTTP202只是入队，平台accepted不是送达/已读。新读/申报接口不解析秘密或发送探针；保存配置仍保留原有provider读取行为。操作和手测见 [通知验证清单](../plans/2026-10-26-notification-verification.md)。
