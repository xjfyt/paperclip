# 备份、升级与回退

> **对应代码** — `cli/src/commands/db-backup.ts`、`cli/src/index.ts`、`server/src/config.ts`、`server/src/services/idle-database-backup.ts`、`packages/db/src/migrations/`
> **维护提示** — 备份命令、目录、迁移、秘密、存储或回退约束变化时更新
> **最后验证** — 2026-10-30（对照 CLI、迁移换行守卫与持久化回归；未声明既有生产数据恢复演练通过）

## 一、明确备份集合

数据库逻辑备份包含应用、迁移历史和插件数据库 schema，但不包含上传文件、工作区和本地秘密主密钥。恢复前需把逻辑状态与实际字节、owner 和配置对应起来。

| 必备项 | 记录与保全 |
|---|---|
| 数据库 | 实例、数据库版本、备份时间、迁移 journal、可恢复备份及校验摘要 |
| 上传/对象存储 | provider、目录/bucket、对象字节、与 DB 一致的保全窗口 |
| 工作区 | 受管和显式目录、重要未提交文件、权限与 owner |
| 秘密 | 匹配的本地 master key 或 provider 配置，由受控秘密系统保全 |
| 运行和配置 | 应用完整 SHA/镜像 digest、适配器版本、部署变量引用、外部待处理 job/投递 |

原始秘密与备份文件不提交 Git。仅复制正在运行的 embedded PostgreSQL 目录不等于已取得一致性备份。默认位置与完整限制见[数据库合同](../../doc/DATABASE.md)。

## 二、创建并核对逻辑备份

选择明确实例再运行 CLI；以下 `./tmp/paperclip-dev` 只是示例，应替换成待备份实例实际的状态根目录。

```sh
node cli/node_modules/tsx/dist/cli.mjs cli/src/index.ts db:backup --data-dir ./tmp/paperclip-dev --json
```

该命令从仓库根目录运行当前源码。可替换路径、ID 或正文的参数应直接传给 CLI，不经包管理器脚本再拼接成 shell 字符串，详见[CLI 调用约束](../../doc/CLI.md#offline-and-air-gapped-use)。核对命令成功、实际输出位置、文件大小/摘要与数据库身份。`--dir` 可选择受控备份输出位置；保留策略按当前配置和 CLI 参数处理。根 `pnpm db:backup` 使用 shell wrapper，在 Windows 下优先使用上述 CLI 入口。

自动备份的默认间隔/保留期及 worktree 例外见[开发合同](../../doc/DEVELOPING.md#automatic-db-backups)，不能仅因默认启用就认为已有可恢复备份。把恢复验证做在隔离测试环境，确认 schema、典型数据、权限、秘密解密和附件读取；不得覆盖真实实例进行演练。

Windows 的 idle 停机备份门禁必须完成 gzip 全量读取、文件字节 flush 和路径身份复核，不能仅因 SQL 可读就清除 wake marker。该门禁不自动改变既有只读备份的权限；无法取得文件 flush 所需写句柄时保持拒绝和 marker，原备份仍可通过普通读取/恢复入口使用。只对 Windows Node 不支持的目录句柄 flush 采用明确的兼容分支，文件写入/flush 的 EIO、ENOSPC 等真实错误仍失败；这不是断电恢复验收证明。

## 三、升级顺序

升级前先固定输入并保留可回退的整套数据，二开专项步骤见[部署合同](../../doc/mimouse/deployment.md)。

1. 核对目标完整提交、部署物及当前实际版本，阅读 schema/migration 与适配器合同差异。
2. 保全上表各项，确认最近备份可恢复；记录外部未知任务和投递，暂停相关新执行入口。
3. 在隔离恢复副本应用当前完整迁移链并验证；不能只挑文档里提到的早期迁移。
4. 按实际启动/迁移流程部署，核对健康、认证、公司/任务、审计、秘密解密、附件及典型工作区读取。
5. 外部集成保持保守状态，按批准测试目标逐项启用并留回执；部署成功不授予外发、收费、签名或业务写入权限。

`pnpm db:migrate` 使用当前实例/配置选择的数据库；执行前确认目标，不能把示例开发 URL 用于生产。已经应用的迁移不重写，不为“修复历史”直接清空台账。

### 1、Windows 旧检出的迁移字节

迁移源文件按 `.gitattributes` 固定为 LF；2026-10-30 的本机修复只恢复换行字节，没有修改 SQL 内容或已发布的摘要常量。旧 Windows 检出可能曾以 CRLF 字节创建迁移 receipt。新检出规则不证明这些既有数据库能直接升级。

升级前保全原程序/迁移文件、数据库备份与原 journal，在隔离恢复副本先运行只读的 `inspectMigrations` 并比对 receipt hash、迁移文件原字节和对应 schema。当前入口发现未匹配 LF 文件、但精确匹配其 CRLF 版本的 receipt 时，会在检查、协调历史和自动迁移前报 `Migration line-ending mismatch` 并阻断，不自动补写历史。其它部分 hash 匹配和不支持的 statement 仍无法完整证明旧历史；schema 中存在同名表也不能证明数据迁移已完成。若已执行迁移被列为 pending、出现 journal drift 或 hash 无法对应，应停止升级，保留证据并人工评估。不要直接执行 `db:migrate` 试错，不删除 journal、不改已部署 hash、不自动重放，也不通过重新生成空库替代既有数据恢复验收。

## 四、回退与未知操作

先停止新的外部派发，再核对已发出的 job/通知/GitLab 请求。应用回退不证明供应商任务停止，也不自动撤销写入或恢复已删除数据。

数据库前向迁移后的旧程序兼容性需独立验证；不要默认旧版本能读取新 schema。必要时在隔离环境验证整套备份恢复，并由明确负责人决定切换。保留必要台账、主密钥和迁移证据，不删除未知投递或运行记录以消除告警。

WorkBuddy 0338 的旧公司级凭据隔离与重新授权、SSO 恢复、公司永久删除等具有专门边界，按[二开部署合同](../../doc/mimouse/deployment.md)和功能文档处理。普通应用回退不提供万能撤销。

## 五、恢复验收记录

记录备份集合、应用/数据库版本、输入摘要、恢复目标、命令、实际用时、检查结果及缺失项。升级前副本演练、最终包验证、真实部署和真实业务验收分别记录，不把空库迁移或源码构建写成既有数据灾难恢复通过。
